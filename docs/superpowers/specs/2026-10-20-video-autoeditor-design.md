# 영상 자동 편집 프로그램 — 설계 문서

작성일: 2026-10-20 · 상태: **확정 — 사용자 승인 완료 (2026-10-20). 구현 계획 단계.** 추가 수정은 첫 버전 완성 이후.

표기: **[결정]** = 사용자가 정한 것 · **[내 판단]** = 대화에서 정하지 않아 제가 고른 것(바꿀 수 있음) · **[열린 질문]** = 사용자만 답할 수 있는 것

---

## 1. 무엇을, 왜

사용자가 영상을 올리고 "이런 느낌으로 만들어줘"라고 레퍼런스 영상을 고르면, AI가 그 레퍼런스의 편집 방식을 따라 영상을 자동으로 편집하고, 품질 검수까지 마친 결과물을 돌려준다. 사용자가 확정하면 저장하고, 유튜브(일반·숏츠)·인스타 릴스·네이버 클립에 올릴 수 있다.

핵심 가치는 **"영상 편집을 몰라도, 잘 나가는 영상의 문법으로 바로 편집된 결과가 나온다"** 이다. 편집 자체가 제품의 중심이고, 업로드는 마무리 편의 기능이다.

## 2. 사용자 흐름 [결정]

1. 영상 업로드 + **영상 설명 입력란(자연어, 선택)** — 예: "본 영상은 골프 레슨 영상입니다."
   - 업로드 아래에 **용도 선택 옵션**: 게시물 영상용(가로) / 릴스·숏츠용(세로). 업로드하면 AI가 용도를 **자동 인식**해 미리 선택해 두고, 사용자가 바꿀 수 있다. [결정 2026-10-20]
   - 용도에 따라 가로 또는 세로로 **알아서 크롭해서 편집**하고, 세로로 자를 때는 **사람이 화면 중앙에 오게** 한다. [결정 2026-10-20]
2. 레퍼런스가 있으면 mp4 파일 또는 영상 링크를 첨부한다.
3. 레퍼런스가 없으면 영상에 어울리고 조회수가 잘 나오는 영상/릴스 목록을 가져와 보여 준다.
   - 설명을 적었으면 그 설명으로 검색한다.
   - **비웠으면 AI가 영상을 직접 분석**(음성 + 화면)해서 어떤 영상인지 파악하고 그 기준으로 검색한다.
4. 사용자가 추천 목록에서 레퍼런스를 고른다.
5. **참고 요청 입력란(자연어, 선택)** — "레퍼런스에서 어떤 부분을 참고했으면 하는지." 비웠으면 AI가 레퍼런스를 참고해 최대한 좋은 퀄리티로 알아서 편집한다.
6. hyperframes로 자동 편집 → **검수**(자막 오타·인식 오류, 화질 저하, 전체 퀄리티) → 사용자에게 전달.
7. 사용자가 확인 후 **Confirm** → DB 저장, History 목록에 표시 → 업로드 화면.
8. 업로드 버튼: 유튜브 게시물 / 유튜브 숏츠 / 인스타 릴스 / 네이버 클립 **각각 개별 버튼** + **전체 일괄 업로드 통합 버튼**.

## 3. 목표 · 비목표 · 안티골

**목표**
- 업로드 → 확정까지 사용자가 편집 지식 없이 끝낼 수 있다.
- 용도(게시물용 가로 / 릴스·숏츠용 세로)에 맞게 **자동으로 비율을 바꾸고**, 세로로 자를 때 주인공이 화면 중앙에 온다.
- 자막이 음성과 맞고 오타가 없으며, 원본보다 화질이 눈에 띄게 나빠지지 않은 결과물만 전달된다.
- 확정한 영상은 언제든 History에서 다시 보고, 플랫폼별로 따로 또는 한꺼번에 올릴 수 있다.
- UI/UX와 편집 결과물이 **전문가가 만든 수준**으로 보인다 [결정].

**비목표 (이번 범위 밖)**
- 카메라 워크, 실사 합성 VFX 따라 하기 [결정 — 나중 이야기]. hyperframes로 가능한 범위(컷 편집, 자막, 오버레이/제목 카드, 전환, 리프레임, 음악·효과음)만 한다.
- 위 4개 외 플랫폼, 모바일 앱, 결제/구독. [내 판단]
- 인스타 릴스의 "인기 릴스 자동 추천". 공식 API가 없다 → 4번 참고.

**안티골 (기술적으로 동작해도 실패인 것)**
- 검수를 건너뛰거나, 검수가 잡은 자막 오타·화질 문제가 그대로 사용자에게 가는 것.
- **사용자가 누르지 않았는데 게시되는 것.** 게시는 Confirm 후 사용자가 버튼을 눌렀을 때만. [내 판단]
- 레퍼런스 영상의 **원본 화면·음원이 결과물에 그대로 들어가는 것.** 레퍼런스에서는 "편집 방식(스타일)"만 추출하고, 레퍼런스의 영상·음악 소스는 결과물에 쓰지 않는다. 분석 후 다운로드한 레퍼런스 원본은 삭제한다. [내 판단 — 저작권 위험 때문]
- 한 플랫폼 업로드 실패가 다른 플랫폼 업로드나 이미 저장된 영상을 망치는 것.
- 세로로 자른 결과에서 주인공이 화면 밖으로 나가거나 잘리는 것, 크롭 위치가 계속 흔들리는 것.

## 4. 외부 의존과 조사 결과 (확인된 것 / 확인 필요)

| 항목 | 상태 |
|---|---|
| **hyperframes** | `npx hyperframes` 사용. Node 22+ 와 **FFmpeg 필요**. 이 맥은 Node 24는 있고 **FFmpeg·hyperframes가 아직 없음** → 설치 필요. 렌더 품질은 draft → looks → delivery 3단계. |
| **레퍼런스 링크 다운로드** | `yt-dlp` 설치돼 있음(`~/.local/bin`). 플랫폼 약관·저작권 이슈가 있어 **분석 전용 임시 사용**으로 한정. |
| **음성 인식(자막)** | 로컬 whisper 없음. `media-use` 스킬의 전사 경로 또는 whisper 계열 설치 중 빌더가 선택. 한국어 정확도를 실제 영상으로 검증할 것. |
| **유튜브 업로드** | 공식 Data API(OAuth). 구글 앱 심사 전에는 업로드된 영상이 비공개로 잠기고, 일일 쿼터가 작다(영상 1건당 소모량이 커서 하루 수 건 수준 — **정확한 수치는 구현 시 확인**). 숏츠는 별도 API가 아니라 세로 영상 + 길이 규격으로 구분된다. |
| **유튜브 인기 영상 검색** | 공식 API로 조회수 기준 검색 가능 → **레퍼런스 추천은 유튜브부터** [내 판단]. |
| **인스타 릴스 업로드** | Graph API(비즈니스/크리에이터 계정 + 페이스북 페이지 + 앱 심사). **영상이 공개 URL로 접근 가능해야** 한다. 선례: `~/Desktop/naver-news-autoshorts/upload_instagram.py` (R2 공개 스토리지에 올린 뒤 릴스 컨테이너 생성 → 처리 대기 → publish). 자격 증명은 환경변수. |
| **인스타 인기 릴스 추천** | 공식 API 없음. 인스타 레퍼런스는 사용자가 링크/mp4로 직접 넣는 방식으로 둔다. [내 판단] |
| **네이버 클립 업로드** | **공개 업로드 API를 확인하지 못했다.** 구현 첫 단계로 조사(스파이크)부터 한다. 막혀 있으면 버튼은 유지하고 "영상 다운로드 + 제목/설명 복사" 보조 화면으로 대체한다. [내 판단] |

## 5. 편집 파이프라인 (빌더 가이드)

1. **입력 이해** — 음성 전사 + 프레임 샘플링으로 "이 영상은 무엇인가"(주제·장르·길이·비율·해상도·화자 수) 요약을 만든다. 설명이 있으면 그것을 우선하고, 분석 결과와 어긋나면 설명을 따른다.
2. **레퍼런스 분석 → 스타일 명세서(JSON)** — 길이·비율, 컷 템포, 첫 3초 훅 구조, 자막(위치·크기·색·강조·등장 방식), 오버레이(제목 카드·하단바), 전환, 음악 분위기, 장면 구성. 어떤 항목이든 "따라 할 수 있는 것 / 근사만 가능한 것 / 불가능한 것"을 표시한다.
3. **자연어 해석** — 참고 요청 입력을 명세서의 "가져올 항목 / 제외할 항목 / 바꿀 항목"으로 해석한다. 비어 있으면 명세서 전체를 품질 우선으로 적용. **렌더 전에 "이렇게 이해했어요" 카드를 보여 주고 사용자가 승인/수정**한다. 불가능한 요청은 이 카드에서 "비슷하게만 가능"이라고 정직하게 알린다. [내 판단]
   - 설명 입력을 비웠을 때의 AI 분석 결과도 같은 방식으로 한 줄 확인 후 검색한다. [내 판단]
4. **편집** — 무음·군더더기·NG 구간 컷(`yt-edit` 방식) → hyperframes 컴포지션 구성(`hyperframes` 스킬이 진입점, 자막은 `embedded-captions`, 오버레이는 `talking-head-recut` 등 하위 스킬 활용) → `check` → 렌더. 최종 미리보기를 먼저 확인한 뒤 delivery 렌더.
5. **검수 게이트 (전달 전 필수)** — 자동 점검 후, 문제가 있으면 해당 부분만 재작업(최대 2회). 점검 항목:
   - 자막: 음성 재전사와 대조한 오타·인식 오류, 싱크 어긋남, 화면 밖 잘림/겹침.
   - 화질: 원본 대비 해상도·비트레이트 하락, 블러·블록 노이즈, 검은 프레임·프레임 드롭.
   - 오디오: 클리핑, 음량 급변, 싱크.
   - 규격: 길이·비율이 선택된 용도에 맞는지.
   - 리프레임: 주 인물이 프레임 밖으로 잘리거나 중앙에서 크게 벗어나는 구간, 크롭 위치의 흔들림.
   - 해상도: 크롭 후 확대 배율과 그에 따른 선명도 하락(5-1 참고).
   - 재작업 후에도 남은 문제는 **숨기지 않고 검수 리포트에 표시한 채** 전달한다. [내 판단]
6. 검수 리포트(무엇을 봤고 무엇을 고쳤는지)를 결과 화면에 함께 보여 준다.

### 5-1. 용도 결정과 리프레임 [사용자 요청 2026-10-20]

용도는 **게시물 영상용(가로 16:9, 1920×1080)** 과 **릴스·숏츠용(세로 9:16, 1080×1920)** 두 가지.

- **자동 인식** [내 판단]: 업로드 영상의 비율·길이, 레퍼런스의 비율·길이(있으면 강한 신호), 영상 설명을 종합해 용도를 추정하고, 화면에 **미리 선택된 상태**로 보여 준다. 사용자가 언제든 바꿀 수 있고 **사용자가 고른 값이 항상 우선**한다. 레퍼런스가 세로여도 사용자가 게시물용을 고르면 가로로 만든다(레퍼런스는 스타일만 제공).
- **같은 비율**이면 크롭 없이 그대로 편집한다.
- **가로 원본 → 세로 출력**: 사람 감지·추적으로 프레임마다 크롭 위치를 계산해 **인물이 화면 중앙에 오게** 한다. 작은 움직임은 무시하고 부드럽게 따라가며, 컷이 바뀌면 새로 잡는다. 한 장면에 여러 명이 있으면 모두 들어갈 때는 그 중심, 다 안 들어가면 말하는 사람(없으면 가장 크게 보이는 사람)을 우선한다. 사람이 없는 장면은 눈에 띄는 영역, 그것도 없으면 중앙 크롭으로 처리하고 **검수 리포트에 표시**한다. 구현(hyperframes의 영상 위치 키프레임 vs 크롭 경로 사전 계산)은 빌더가 고른다.
- **세로 원본 → 가로 출력**: 세로를 가로로 자르면 화면의 3분의 1만 남아 화질이 크게 깨진다. 기본은 **원본을 가운데에 두고 양옆을 블러 배경으로 채우는 방식**이며, "이렇게 이해했어요" 카드에서 미리 알린다. [내 판단]
- **해상도 한계 (정직하게)**: 1080p 가로 영상을 9:16으로 자르면 약 608×1080 영역만 남고, 1080×1920 출력으로 키우면 **약 1.8배 확대**라 선명도가 떨어진다. 4K 원본은 문제가 거의 없다. 확대 배율을 계산해 검수 리포트에 표시하고 배율이 크면 경고한다. 출력 해상도를 낮출지는 실제 영상으로 보고 빌더가 판단한다.

## 6. 화면 구성

- **새 작업**: 업로드 + 영상 설명 입력 + **용도 선택**(자동 인식 결과가 미리 선택됨: 게시물 영상용 / 릴스·숏츠용) → 레퍼런스(링크/파일 첨부 또는 "추천받기") → 추천 목록(썸네일·조회수·길이) → 선택 → 참고 요청 입력 → "이렇게 이해했어요" 확인 카드.
- **진행 상황**: 분석 → 편집 → 검수 단계 표시. 실패 시 어느 단계인지와 이유를 보여 준다.
- **결과 확인**: 영상 미리보기 + 검수 리포트 + **Confirm** / 수정 요청.
- **History**: 확정된 영상 목록(썸네일, 날짜, 플랫폼별 업로드 상태), 클릭 시 상세·재업로드.
- **업로드**: 4개 플랫폼 개별 업로드 버튼 + 통합 일괄 업로드 버튼. 결과물의 용도에 맞는 플랫폼(게시물용 = 유튜브 게시물 / 릴스·숏츠용 = 유튜브 숏츠·인스타 릴스·네이버 클립)만 활성화하고, 맞지 않는 버튼은 이유와 함께 비활성 표시한다. 통합 버튼의 범위는 11번 질문 3. 플랫폼별 상태(대기/진행/완료/실패+사유+재시도)를 독립적으로 표시. 제목·설명·해시태그는 플랫폼별로 편집 가능.
- UI 구현 시 `impeccable`, `ui-ux-pro-max`, `design-taste-frontend` 등 설치된 디자인 스킬을 쓴다 [결정]. 한국어 UI. [내 판단]

## 7. 데이터

## 8. 만드는 방식 [내 판단 — 빌더가 더 나은 근거가 있으면 바꿔도 됨]

- 위치: `~/Desktop/video-autoeditor` (사용자의 다른 프로젝트와 같은 곳).

- AI 호출 방식(`claude -p` 로그인 방식 vs API 키)은 빌더가 고른다. 단, **돈·크레딧이 드는 작업은 비용을 알리고 시작**한다(사용자의 기존 규칙).
- 범위는 **본인 한 명이 쓰는 앱**으로 시작하되, 나중에 여러 사용자로 늘릴 수 있게 작업·계정 데이터를 사용자 단위로 나눠 둔다. [결정 — 11번 질문 2]

## 9. 만드는 순서 [내 판단]

핵심 가치(편집)와 가장 큰 불확실성(업로드)을 먼저 확인하는 순서.

0. **환경 + 스파이크**: FFmpeg·hyperframes 설치, 샘플 영상 1개로 "업로드 → 레퍼런스 링크 → 편집 결과" 한 번 관통. 동시에 **네이버 클립 업로드 가능 여부 조사**.
1. **편집 코어**: 입력 이해 → 용도 판별 → 레퍼런스 분석 → 자연어 해석 → 편집 + 리프레임(5-1) → 검수 게이트.
2. **화면 + 새 작업 흐름**, 결과 확인.
3. **레퍼런스 추천**(유튜브 검색) + 설명 비었을 때의 영상 분석.
4. **Confirm · DB · History**.
5. **업로드**: 유튜브(일반·숏츠) → 인스타 릴스 → 네이버 클립 → 통합 버튼.

## 10. 성공 기준

- 샘플 영상(후보: `~/Desktop/롱아이언_릴스_편집본.mp4`, 이름으로 보아 골프 영상) + 레퍼런스 링크 1개로 **검수를 통과한 결과 mp4**가 나온다.
- 일부러 오타가 나는 자막/저화질 입력을 넣었을 때 검수가 이를 잡아낸다.
- Confirm 후 DB에 저장되고 History에 나타난다.
- 각 플랫폼 업로드를 **비공개/테스트 상태로** 실제로 성공시켜 본다.
- **UI는 실제로 띄워서 눈으로 확인한다.** 테스트 통과만으로 완료라 하지 않는다 (사용자가 여러 번 겪은 문제).
- 요청한 범위 밖은 바꾸지 않는다. 범위 밖 발견은 제안만 한다.

## 11. 확정된 질문 (2026-10-20, 사용자가 "추천대로"로 확정) [결정]
